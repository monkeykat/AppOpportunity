# Phase 2.1: Investigation Quality Improvements

## Goal

Phase 2 has already been implemented. Do not redesign or replace Phase 2.

This phase improves the quality, reliability, and usefulness of the existing investigation process. It addresses these weaknesses in the original Phase 2 design:

1. Preserve research evidence instead of storing only AI summaries.
2. Prevent investigations from performing unlimited research.
3. Improve complaint analysis by identifying repeated patterns.
4. Separate evidence from AI interpretation.
5. Make scoring more explainable.
6. Force the system to consider reasons an opportunity may fail.
7. Improve handling of incomplete or failed investigations.
8. Improve calibration of final opportunity scores.

Keep the system simple. Do not introduce agents, frameworks, or complex pipelines. Do not rewrite working Phase 2 functionality unless necessary.

## Important Rule

Phase 2 must already work before implementing Phase 2.1. Phase 2.1 modifies and improves the existing implementation incrementally.

## Core Improvement

The existing pipeline is approximately:

```text
WEB RESEARCH
    |
    v
OLLAMA ANALYSIS
    |
    v
SUMMARY
    |
    v
FINAL SCORE
```

Improve it to:

```text
PUBLIC RESEARCH
    |
    v
RAW EVIDENCE
    |
    v
OBSERVATIONS
    |
    v
OLLAMA ANALYSIS
    |
    v
SCORING
    |
    v
SKEPTICAL FINAL REVIEW
    |
    v
FINAL SCORE
```

The important distinction is:

```text
EVIDENCE is not the same as AI INTERPRETATION
```

The system should preserve enough evidence to make each investigation understandable later.

## 1. Preserve Raw Research Evidence

### Problem

The original Phase 2 design primarily stores summaries generated by Ollama. Later, it may be unclear:

- How many users complained.
- What users actually said.
- Whether a complaint was repeated.
- Whether Ollama overstated the problem.

The investigation should preserve some of the evidence used to generate its conclusions.

### Database Changes

Continue using the existing Phase 2 database and `investigations` table. Do not create additional tables.

Add these optional JSON-text fields to the existing `investigations` table:

- `raw_reviews`
- `raw_competitors`
- `raw_alternatives`

Store only the sample used during the investigation. Do not attempt to store every review or unlimited research data.

### `raw_reviews`

Store a reasonable sample of collected reviews, for example:

```json
[
  {
    "rating": 1,
    "text": "Lost all of my fishing history after the update."
  },
  {
    "rating": 2,
    "text": "Too many advertisements."
  },
  {
    "rating": 1,
    "text": "The app crashes whenever I save a catch."
  }
]
```

### `raw_competitors`

Store competitor information collected during research. Available information may vary.

```json
[
  {
    "name": "Competitor A",
    "description": "Fishing log application.",
    "rating": 4.2,
    "popularity": "500K+ installs"
  },
  {
    "name": "Competitor B",
    "description": "Fishing social network.",
    "rating": 3.8,
    "popularity": "100K+ installs"
  }
]
```

### `raw_alternatives`

Store identified alternatives and workarounds.

```json
[
  "Paper fishing journal",
  "Spreadsheet",
  "Phone notes",
  "Google Maps",
  "Photos",
  "Facebook fishing groups"
]
```

## 2. Add Research Limits

Phase 2 allows web research. Without limits, an investigation could become excessively large. The goal is to collect enough evidence, make a reasonable decision, and stop.

Add these centralized configuration values:

```text
MAX_REVIEWS_PER_APP=30
MAX_COMPETITORS=10
MAX_SEARCH_RESULTS_PER_TOPIC=10
MAX_RESEARCH_PAGES=30
```

Keep these values in `config.py` or the existing configuration mechanism.

- `MAX_REVIEWS_PER_APP`: Maximum number of reviews collected for analysis. Prioritize 1-star, 2-star, and 3-star reviews, while including positive reviews.
- `MAX_COMPETITORS`: Maximum number of competitors investigated.
- `MAX_SEARCH_RESULTS_PER_TOPIC`: Maximum search results examined for one research topic.
- `MAX_RESEARCH_PAGES`: Maximum web pages opened during one investigation.

The implementation should reasonably enforce these limits. A simple counter is sufficient; do not build a complicated crawler.

## 3. Improve Complaint Analysis

### Problem

The system should identify repeated problems, not individual angry users.

### Review Collection

Collect a mixture of:

- 1-star reviews
- 2-star reviews
- 3-star reviews
- Positive reviews

Prioritize lower-rated reviews because they are more likely to reveal problems. Also collect positive reviews to identify:

- Features users value.
- Reasons users choose the app.
- Features a competing product must preserve.

### Complaint Analysis Prompt

Provide Ollama with structured review information:

```json
[
  {
    "rating": 1,
    "text": "Lost all my fishing history."
  },
  {
    "rating": 2,
    "text": "The application crashes constantly."
  },
  {
    "rating": 1,
    "text": "Too many advertisements."
  }
]
```

Ask Ollama to identify:

1. Repeated complaints.
2. Serious complaints.
3. Missing features.
4. Feature requests.
5. Positive features users value.
6. Potential improvements.
7. Whether each complaint appears solvable.

Do not treat a single complaint as strong evidence.

### Complaint Analysis Output

Internally, request structured JSON such as:

```json
{
  "repeated_complaints": [
    {
      "issue": "Data loss",
      "frequency": "Repeated",
      "severity": "High",
      "solvable": true
    },
    {
      "issue": "Excessive advertising",
      "frequency": "Repeated",
      "severity": "Medium",
      "solvable": true
    }
  ],
  "feature_requests": [
    "Cloud backup",
    "Better location tracking"
  ],
  "positive_features": [
    "Catch logging",
    "Fishing history"
  ]
}
```

The system does not need to store this exact JSON separately. Use it to generate the concise `complaint_analysis`. Keep the raw review sample in `raw_reviews`.

## 4. Separate Evidence from Interpretation

The conceptual process should be:

```text
EVIDENCE
    |
    v
OBSERVATIONS
    |
    v
INTERPRETATION
    |
    v
FINAL JUDGMENT
```

### Evidence

Examples:

- 500K+ installs
- 4.1 rating
- 5,000 reviews
- Multiple competitors
- Repeated complaints about advertisements
- Active Reddit discussions
- Users using spreadsheets as workarounds

These are observations from public research.

### Interpretation

Examples:

- There appears to be meaningful demand.
- Advertising may be frustrating users.
- Existing products may not fully solve the problem.
- Users may be combining multiple tools.

These are interpretations, not facts.

### Final Judgment

Example:

> The market appears promising because there is evidence of demand and repeated user frustration. However, multiple established competitors create moderate competitive pressure.

Do not allow Ollama to present speculation as fact. Prefer cautious language such as:

- appears
- suggests
- may indicate
- there is evidence of
- the available research suggests

Avoid unsupported language such as:

- definitely
- guaranteed
- proves
- will succeed

This is exploratory research, not a scientific market study.

## 5. Improve Scoring Explanations

Continue using these 1-10 scores:

- `build_difficulty`
- `proprietary_dependency`
- `market_potential`
- `competition_level`

Scores should be based on explicit reasoning. Do not add separate database columns for every score explanation. Incorporate explanations into existing analysis fields such as `app_analysis`, `competitor_analysis`, and `summary`.

### Build Difficulty

Ask Ollama to estimate the difficulty of building a useful competing MVP, not a perfect clone. Consider:

- Number of major features
- Backend requirements
- Third-party APIs
- Mobile development
- Real-time functionality
- AI requirements
- Specialized hardware
- Data requirements

Return:

```json
{
  "score": 1,
  "reason": "Short explanation"
}
```

### Proprietary Dependency

Evaluate whether the product depends on something difficult to reproduce, including:

- Proprietary data
- Private databases
- Exclusive partnerships
- Network effects
- User-generated data
- Specialized hardware
- Patented technology
- Professional expertise
- Regulatory barriers

Return a score and short reason.

### Market Potential

Estimate market potential using available evidence, including:

- Install counts
- Review counts
- Number of competitors
- Community activity
- Search results
- Public discussion
- Evidence of willingness to pay
- Repeated demand

Return a score and short reason.

### Competition Level

Estimate how difficult it would be for a new product to compete. Consider:

- Number of competitors
- Competitor quality
- Market leaders
- Brand recognition
- Switching costs
- Network effects

Return a score and short reason.

## 6. Improve Competitor Research

A competitor does not have to be an Android app. Consider:

- Android applications
- iOS applications
- Web applications
- SaaS products
- Desktop software
- Industry software
- Physical products
- Generic software

The important question is: what else solves the same problem?

Do not limit competitor research to Google Play. Identify approximately 3-10 relevant competitors when possible. For each, collect whatever public information is reasonably available:

- Name
- Type
- Description
- Rating
- Popularity
- Major strengths
- Major weaknesses

The goal is to understand whether the market is empty, moderately competitive, crowded, or dominated by one player.

## 7. Improve Alternative and Workaround Research

Ask:

> How do people solve this problem without using this app?

Look for:

- Spreadsheets
- Paper notebooks
- Notes applications
- Photos
- Email
- Generic software
- Websites
- Social media
- Facebook groups
- Reddit
- YouTube
- Physical tools
- Manual processes
- Multiple separate applications
- Doing nothing

Explicitly investigate what combination of tools users stitch together.

For example, users tracking fishing activity might combine:

```text
Phone camera + Notes + Google Maps + Weather application
```

This may indicate that users are assembling their own workflow, which can be more interesting than simply finding a bad competitor.

## 8. Add Opportunity Skepticism

An LLM may see a low rating and many downloads and conclude that the opportunity is automatically attractive. The system should actively look for reasons not to pursue it.

During final analysis, ask:

> Why has this problem not already been solved better?

Consider:

- Market too small
- Technology too difficult
- Data too expensive
- Users unwilling to pay
- Strong network effects
- Regulatory barriers
- Existing solutions are good enough
- Problem is seasonal
- Market is declining
- Problem is not actually important
- Professional expertise is required
- Customer acquisition is difficult

Require Ollama to identify the strongest argument against building a competing product. This should influence the final analysis.

## 9. Improve Final Analysis

The final analysis should include:

- App analysis
- User analysis
- Complaint analysis
- Competitor analysis
- Alternative analysis
- Build difficulty
- Proprietary dependency
- Market potential
- Competition level
- Strongest argument against the opportunity

The final prompt should tell Ollama:

- Do not assume a poorly rated app is a good opportunity.
- Do not assume a popular app can easily be competed with.
- High install counts do not automatically indicate willingness to pay.
- User complaints are not automatically solvable.
- A lack of competitors does not automatically indicate demand.
- Consider demand, audience, repeated complaints, solvability, valued features, competitors, alternatives, workarounds, build difficulty, proprietary barriers, network effects, competition, differentiation, and reasons the opportunity may fail.
- Actively look for reasons not to pursue the opportunity.
- Use cautious language when evidence is limited.
- Strong opportunities should be rare.

The final JSON must contain:

```json
{
  "final_score": 1,
  "recommendation": "PASS",
  "summary": "Concise explanation of the opportunity, major risks, and reasons for the recommendation."
}
```

## 10. Improve Score Calibration

LLMs naturally tend to give moderately positive scores. Strong opportunities should be uncommon.

### 1-3: `PASS`

Use when there is little evidence of demand, the market appears too small, the problem is not important, competition is overwhelming, major proprietary barriers exist, build difficulty is excessive, or users appear unwilling to pay.

### 4-5: `INVESTIGATE_FURTHER`

Use when some interesting signals exist but important evidence is missing or major uncertainty remains.

### 6-7: `PROMISING`

Use when there is evidence of demand, a clear problem, potentially solvable weaknesses, and a reasonable path to building a useful product, while important risks still exist.

### 8-10: `STRONG_OPPORTUNITY`

These scores should be rare. A score of 8 or higher requires strong evidence of:

- Meaningful demand
- Clear user problems
- Repeated and solvable complaints
- Achievable product requirements
- No overwhelming proprietary barriers
- A plausible competitive advantage

Do not assign 8 or higher simply because the existing application has a low rating.

## 11. Improve Investigation Status Handling

Continue using:

- `PENDING`
- `IN_PROGRESS`
- `COMPLETE`
- `FAILED`

When an opportunity is selected, immediately create or update the investigation as `IN_PROGRESS` before beginning research.

Set `COMPLETE` only after research, analysis, scoring, and the final recommendation successfully finish.

If an unexpected error occurs, set `FAILED` and record enough information in logs or notes to understand the failure. Do not create a complicated error-management system.

Phase 2.1 does not need checkpoint-level recovery. If an investigation is interrupted, use a simple policy: mark it failed or restart it. Do not build a complex resumable workflow.

### Recommended Selection Logic

1. Do not select `COMPLETE` investigations.
2. Prefer the highest-scoring uninvestigated opportunity.
3. Handle `FAILED` investigations according to a simple retry policy.
4. Do not automatically repeat successful investigations.

## Important Rules

1. **Do not redesign Phase 2.** Preserve working functionality.
2. **Preserve evidence.** Store reasonable samples of reviews, competitors, alternatives, and workarounds.
3. **Bound research.** Respect `MAX_REVIEWS_PER_APP`, `MAX_COMPETITORS`, `MAX_SEARCH_RESULTS_PER_TOPIC`, and `MAX_RESEARCH_PAGES`.
4. **Look for patterns.** Do not treat one complaint, Reddit comment, or forum post as strong evidence.
5. **Separate evidence from interpretation.** Clearly distinguish what was observed from what the system thinks it means.
6. **Be skeptical.** Actively search for reasons the opportunity may fail.
7. **Make strong scores rare.** Multiple pieces of supporting evidence are required.
8. **Keep it simple.** This remains a small Python MVP.

## Core Concept

The original Phase 2 asks:

> Is this app worth investigating?

Phase 2.1 improves the question to:

- What evidence suggests this is an opportunity?
- What evidence suggests it is not?
- Are the user problems repeated?
- Are those problems actually solvable?
- Can we realistically build something better?
- Why has someone not already solved this?
- Is the evidence strong enough to justify spending more time?

The result should be a Phase 2 investigation system that is more evidence-based, more skeptical, and more useful while remaining small and simple.
